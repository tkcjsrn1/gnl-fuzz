# gnl-fuzz: 내 get_next_line을 퍼징으로 다시 검증하기

42 Tokyo에서 작성한 `get_next_line`을 **커버리지 기반 퍼징(libFuzzer, AFL++)**으로 다시 검증한 기록입니다.
크래시만 보는 대신, **"반환 결과가 맞는가"를 자동으로 판정하는 정확성 오라클**을 붙였습니다.

> 작업 방식: 퍼징 하네스·Makefile·README는 AI 코딩 도구(Claude)와 함께 작성했습니다. 대상 코드(`targets/`)는 42 과제 때 직접 작성한 원본입니다.

## 결과 요약

| 대상 | 결과 |
|---|---|
| 2025-08-14 버전 (`targets/v1_2025-08-14`) | **버그 2개 발견**: EOF 이후 재호출 시 use-after-free, read마다 메모리 누수 → [findings](findings/README.md) |
| 최종 버전 (`targets/v2_final`) | libFuzzer 30분 + AFL++ 30분, 합계 약 7,150만 회 실행 동안 오라클 위반·메모리 오류·누수 **0건** |

헤더(`get_next_line.h`)는 두 버전 모두 PC에 남아 있던 원본(2025-08-31)을 사용했습니다. 두 버전의 함수 선언은 같습니다.

## 왜 만들었나

- 당시에는 동료 평가와 Francinette 같은 테스터로 검증했습니다. 둘 다 사람이 미리 떠올린 입력만 확인합니다.
- 퍼저는 사람이 생각하지 못한 입력을 대량으로 만듭니다. 하지만 **무엇이 버그인지 판정하는 기준(오라클)**이 없으면 크래시가 아닌 오답은 놓칩니다.

## 오라클 (`harness/fuzz_gnl.c`)

입력 바이트를 파이프에 넣고, `get_next_line`이 `NULL`을 반환할 때까지 읽으며 다음을 검사합니다.

| # | 검사 | 잡는 버그 예 |
|---|---|---|
| 1 | 반환된 줄을 이어 붙이면 입력과 **바이트 단위로 동일** | 줄 누락, 중복, 순서 뒤바뀜 |
| 2 | 빈 문자열(`""`)을 반환하지 않음 | 경계에서 빈 줄 반환 |
| 3 | `'\n'`은 줄의 마지막 글자로만 등장 | 두 줄이 합쳐져 반환 |
| 4 | `'\n'` 없는 줄은 반드시 마지막 줄 | 마지막 줄 뒤 잔여 데이터 |
| 5 | EOF 이후 재호출 시에도 `NULL` | static 버퍼 잔여 데이터, 해제 후 사용 |
| 6 | 반환 길이가 남은 입력보다 길지 않음 (오버플로 가드) | 버퍼 경계 초과 |

AddressSanitizer, LeakSanitizer, UBSan을 함께 켭니다. 8월 버전의 use-after-free는 #5 단계에서 드러났습니다. 일반적인 테스트는 `NULL`이 나오면 읽기를 멈추기 때문에 밟지 않는 경로입니다.

범위: `'\0'`이 포함된 입력은 텍스트 파일 범위 밖이므로 제외하고, 입력 크기는 4096바이트로 제한합니다(파이프 버퍼 막힘 방지).

## 최종 버전 퍼징 기록

| 도구 | BUFFER_SIZE | 시간 | 실행 횟수 | 커버리지 | 결과 |
|---|---|---|---|---|---|
| libFuzzer + ASan/LSan/UBSan | 1 | 10분 | 6,472,310 | cov 49 / ft 296 | 위반 0 |
| libFuzzer + ASan/LSan/UBSan | 42 | 10분 | 4,913,066 | cov 64 / ft 387 | 위반 0 |
| libFuzzer + ASan/LSan/UBSan | 100000 | 10분 | 2,241,800 | cov 60 / ft 280 | 위반 0 |
| AFL++ + ASan | 42 | 30분 | 57,915,238 | bitmap 52.9%, stability 100% | crash 0, hang 0 |

위반 0건은 "이 입력 범위에서 찾지 못했다"는 뜻이지, 정확성의 증명은 아닙니다. 입력을 4096바이트로 제한했고, `read` 실패나 `malloc` 실패 경로는 이 하네스가 만들지 않습니다(다음 과제: 실패 주입).

## 하네스 자체 검증

오라클이 정말 버그를 잡는지 확인하려고, 따로 만든 테스트용 구현으로 먼저 돌렸습니다.

- 정상 구현: 오탐 없음
- 마지막 줄(`'\n'` 없음)을 버리는 구현: 오라클 #1이 즉시 검출
- 읽기 버퍼를 해제하지 않는 구현: LeakSanitizer가 검출

## 실행 방법

환경: Linux 또는 WSL + clang (macOS 기본 clang은 libFuzzer 미지원 → Docker 권장)

```bash
make run                                   # 최종 버전, BUFFER_SIZE=42, 5분
make run-all TIME=600                      # BUFFER_SIZE 1 / 42 / 100000, 각 10분
make run SRC_DIR=targets/v1_2025-08-14     # 8월 버전 (즉시 크래시)
make afl TIME=1800                         # AFL++ 30분
./bin/fuzz_bs42 findings/bug1_uaf_empty_input.bin   # 크래시 재현
```

## 배운 점

- 퍼징의 성패는 입력 생성보다 **판정 기준**에 달려 있었습니다. 오라클 #5를 넣기 전까지 8월 버전의 use-after-free는 정상 동작처럼 보였습니다.
- 버그 하나를 고친 사본으로 다시 돌려야 그 뒤에 숨은 버그가 보였습니다(Bug 1 → Bug 2).
- 8월 버전의 `SIZE_MAX` 오버플로 가드는 항상 거짓인 검사였습니다. 가드를 "썼다"는 것과 가드가 "동작한다"는 것은 다릅니다.
